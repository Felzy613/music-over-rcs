# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal bot: you text `search <words>` in your own Google Messages "message yourself" chat, get a menu of artists, albums and songs like a streaming app's, and a 👍 on a song sends back the audio file with album art (on an album, its songs and a zip of them). It reaches the phone through a self-hosted mautrix-gmessages bridge and a Matrix (Synapse) homeserver, which run with the bot in one Docker container on Render's free plan (a Cloudflare Worker and an R2 bucket beside it); since 2026-10-16 that is the only place it runs, and the Mac install was removed. Songs come first from Zemer's catalog (`search.zemer.io`, the service the Zemer app searches with: albums and singles of the artists on Zemer's list, audio from YouTube Music through the same InnerTube API the app uses), and, for what Zemer doesn't have, from a local SQLite catalog fed by music-table.com (direct MP3 downloads of mostly new singles on its release posts). New music (the `new` list, the daily message and the alerts for artists you follow) is Zemer's own Latest Releases feed and music-table.com's posts together (the owner's request, 2026-10-28: "Make zemer also the source for new releases"). `README.md` covers the user-facing behavior; `docs/architecture.md` is the fuller code tour. With `PEOPLE` set in Render, other people with their own phone and Google account can use it from their own "message yourself" chat on the same container (the **People** bullet below, `docs/cloud.md` "Other people"); that is deployed and, since 2026-11-09, works live with one person on a different Google account and phone (search, 👍, a song, their own chat found by itself); only a quiet night's traffic with two logins is still unwatched (`PEOPLE` empty and nothing saved is the owner alone, exactly as before).

## Commands

TypeScript runs directly on Node ≥ 22.18 (no build step), and there are **no runtime dependencies** (`node:sqlite`, `node:http`, built-in `fetch`). `npm install` only brings in `typescript` and `@types/node`.

```bash
npm test                          # whole suite, no network (mock servers in test/helpers/)
npm run typecheck                 # tsc, noEmit; covers src, scripts, test and extensions
npm run simulate:web -- --open    # real bot + real site in a browser chat; needs no accounts
npm run simulate:admin -- --open  # the management console on made-up data (mock servers from test/helpers); needs no accounts
npm run matrix                    # run the bridge-route bot in the foreground (needs .env)
npm run library -- <cmd>          # status | sync | scan | prefetch | digest [--days N] [--send]
ADMIN_TOKEN=… npm run cloud:check -- --render https://<your-service>.onrender.com   # is the live host, bridge, bot and Worker healthy
```

Run one test file, or one test by name (invoke `node` directly; `npm test` takes a fixed glob):

```bash
node --disable-warning=ExperimentalWarning --test test/naming.test.ts
node --disable-warning=ExperimentalWarning --test --test-name-pattern="restart" test/bridge-restart.test.ts
```

There is no linter or formatter configured.

## The running bot is on Render, not this folder

The live bot runs from the Docker image Render builds from the `main` branch (service `music-over-rcs`, Ohio (its id and address are in Render's dashboard, not in this repository), free plan; `docs/cloud.md` is the runbook). **Nothing here reaches it until you push and deploy**: push to `main`, then deploy by hand (Render dashboard → *Manual Deploy*, or the Render MCP's `trigger_deploy`); `autoDeploy` is off on purpose. A deploy restarts the bot (about a minute down; texts sent meanwhile are answered afterwards), and deploys queue behind each other, so do not stack them. Changing an environment variable in Render restarts it too, and `.env` here is only for local runs. The `PEOPLE` work is in the tree but has not been pushed or deployed. The live catalog is in the container, backed up to R2; `data/catalog.db` is only what a local `npm run …` uses. The Mac install (`deploy/mac`, launchd) is gone; do not bring it back next to the cloud host, because two bots in one chat both answer. **No more money** (the owner, 2026-10-20): everything stays on Render's free plan and the Cloudflare Workers plan already paid for; recommend only $0 changes (`docs/cloud.md`, "What it costs").

## Architecture

Three layers, in the order a message travels:

1. **Transport** (`ChatClient`: `listMessages`, `sendText`, `sendAudio`, optional `sendImage`, `sendFile` (the album zip), `setTyping`). Implementations: `src/matrix/` (the main route), `src/beeper/`, and the simulator's `SimulatedChat`. The RCS for Business route (`src/rbm/`, `src/handler.ts`, `src/server.ts`, entry `npm start`) is a separate webhook server that calls the bot directly and doesn't get the library features.
2. **`src/runner.ts`** binds the bot to one chat: reads it (a long poll where the chat can, `waitMs`/`MATRIX_SYNC_WAIT_MS`, 25 s; an announcement or stop aborts the wait), ignores its own messages, handles 👍 reactions, numbers, `all`, typing indicators, downloading ahead (an album's songs three at a time, `albumDownloads`/`ALBUM_DOWNLOADS`, each to disk as it arrives, held back by `memoryRoom` and a 40 MB in-flight budget, one at a time after YouTube turned the relay away), spacing audio files by `SONG_GAP_SECONDS`, and sends bot-initiated messages through `announce` (never in the middle of answering a request). Reading the chat never waits for a song on its way (owner's report 2026-10-18): a poll looks each request up and sends a text answer at once, while an answer with a song, picture or album joins a delivery queue (`send`) that runs one at a time in the order asked, because songs must arrive in that order and the host can't hold two downloads (with several chats on a host the one-at-a-time is host-wide: `RunnerOptions.gate`/`gateOwner`, see **People**). An answer's options (its chips and numbers) apply when it is decided, not when it has been sent, and only an answer with options of its own replaces them (an unrelated text leaves a menu pickable; a pick refreshes its two hours). "typing…" stays up while any request is open, and the resume point is saved only when nothing is queued. Each request leaves a `timeline:` line (`src/timeline.ts`: phone→seen, the bot's traced steps, each send, and with `sendStatus` the bridge's word that Google had the messages), each song a `song:` line, each album an `album:` line; `onTimeline` hands them to `/status`. `Runner.tick()` still returns when everything it started has been sent (the tests rely on it); the poll loop uses `poll()`.
3. **`src/bot.ts`** decides what to answer and knows nothing about platforms. It takes text or a postback and returns `Reply[]` (`text`, `image`, `collage`, `audio`, `album`; see `src/types.ts`). **A search is a menu, never a pick** (the owner's design, 2026-10-20; `Fixing PLan.md`): up to 5 artists (🎤), 5 albums (💿, numbered) and 5 songs, one message per line, ranked by `src/ranking.ts` (artists exact > started > a typo away; songs named > every word in the title > only with the artist, most played first; albums named > newest; editions folded), written by `src/menu.ts`, ending with a hint line (`HINT_MARK`) whose postback is `view:<id>`. Nothing is sent or opened on its own, not one exactly named song, not an artist's full name. Every menu, artist page (`artist:<id>`), album (`album:`/`tracks:<id>`: its songs numbered as on the album and a `📦` line, `zip:<id>`) and music-table list is a **view** (`src/views.ts`, catalog table `views`, ids never reused, current one in state `chat.view`): what it is of, and every line it has shown. `songs more`/`albums more`/`artists more` re-ask the source (Zemer's answers are kept 10 minutes), skip what was shown and show the next 8, walking up to the parent view when the current one lacks that kind; bare `more` repeats the last. Every line's postback carries its view (`play:42@41`, `splitPostback`), so a 👍 on a line of an older menu makes it current again; an answer that changes the current view without a list of its own carries that view's options (an empty-text chips reply). Commands: `search`, `artist`/`album`/`song` (one-kind menus; `albums more` is paging, `albums <name>` a search), `zemer` (`youtube`/`yt`), `zip`, `all`, `help` (one message, `helpText`), the music-table lists (`new` also lists Zemer's new releases: `single:<id>` and `album:<id>` lines), follow. Old postbacks still work (`album:` without a view now opens the album). `play()` starts the album lookup (`Finder.fillIn`) alongside the download: the card's `better` cover and the audio's `after` hand-off, which `taggedFetch` waits for before tagging. Slow steps are traced (`handle(msg, trace)`, through an `AsyncLocalStorage`). An `album` reply is a list of song addresses; the runner downloads them to a temporary folder and sends one zip made of the files on disk (`src/library/zip.ts`), split only past `MAX_ZIP_MB` (100: the bridge's and the homeserver's limit), or the songs one by one on a chat with no `sendFile`. The owner wants an album as one zip, not parts (2026-10-18); that is why nothing on the way holds it in memory: the disk folder, the Matrix client's streamed `node:http` upload (Node's `fetch` buffers a whole body), and the bridge patch `deploy/cloud/patches/gmessages-stream-media.patch` (`docs/cloud.md`). The golden menus are tested against what Zemer really answered (`test/fixtures/zemer`, `test/menu.test.ts`).

Entry points wire these together: `src/host.ts` is the best single file to read for how everything is assembled. `startHost` builds what every chat shares, once (catalog, Zemer's list and the one gated `checkAudio`, music-table source, YouTube Music, releases, library jobs, health, extensions, the console's `provide`, the delivery gate, the memory guard) and `addChat(host, person, { token, roomID, … })` builds one person's own chat (their Matrix client and counters, bot, runner, bridge watch, startup hello, place among the jobs' recipients; `removeChat` takes it off). Every bot is built from the same `sources` and `checkAudio` objects; only the owner's has `artistList`, `assistant`, the waiting-artist notice, the add-ons and OneDrive's archive. `src/matrix-main.ts` is just the `npm run matrix` entry over it (one host, the owner's one chat), and the one `cloud-main.ts` imports.

Behind the bot:

- **`src/catalog.ts`**: one SQLite file (WAL, shared with the CLI tools): tracks + FTS, artists, site posts, plays, follows, audio cache, `message_links`, and a `state` key/value table. The background jobs persist their progress there, so restarts resume. Per-person state has a `chat` column (`views`, `plays`, `follows`; `''` is the owner) and the `deliveries` table (see **People**).
- **`src/library/jobs.ts`** (`LibraryJobs`): ticks once a minute, doing one thing at a time (site sync every 3 h, Zemer's new-releases feed every 30 min, prefetch, RSS check every 15 min while following anyone, daily message, follow alerts outside quiet hours, one-time full-site scan). The daily message and the alerts carry Zemer's releases beside the site's. The jobs that read a source (site sync, Zemer's feed, prefetch, scan) run once for everybody; the daily message and the alerts go to each registered recipient (`addRecipient`/`removeRecipient`, see **People**). The library tests drive it on a fake clock.
- **`src/sources/zemer.ts`**: Zemer's catalog. `ZemerSearch` is the client for `search.zemer.io` (`/search` sorted into artists, songs, videos, albums, singles, `k=50` because Zemer's order isn't by plays; `/artist`; `/album`; always `allowFemale=0&blockVideos=0&kidZone=0`, since the server leaves in whatever isn't said; searches, artist and album pages kept 10 minutes). `find` returns each song's `id` (video id), `plays` and `video`, folds duplicates keeping the most played copy, lists a video only when no song has it, and returns singles apart from albums (`Findings.singles`; the menu lists a single as a song). `createZemerFinder` makes it the bot's `Finder` (and its `albums` opener): it re-checks every result against the local whitelist by channel id, stores only the songs it shows (`FoundSong.keep`), and falls back to YouTube Music's own InnerTube search when Zemer can't be reached or `ZEMER_SEARCH=off`; **that is what the live host does, since `search.zemer.io` has refused the bot since 2026-10-29** (the start-up line says "Zemer off (YouTube Music search instead)"), so the fallback is a full source: besides songs and albums it asks YouTube Music's artists search (held to the whitelist by channel id) and, for the one or two artists the words name, opens their artist page (`YouTubeMusic.artist`: every album, every single, marked `single` and listed with the albums newest first, and the hundred most played songs with plays), which is also what a 👍 on a 🎤 opens (`fromYouTube`/`artistFromYouTube` in `zemer.ts`). "search album <words>" (and "search <words> album") is the kind search "album <words>" (`searchFor` in `bot.ts`). A song with no cover gets its album's at send time (`Finder.cover`). The owner wants Zemer first and music-table.com only as the fallback (2026-10-17): "If both have it, rather use Zemer."
- **`src/sources/zemer-releases.ts`**: Zemer as a source of new releases. `ZemerReleases` reads the feed behind the Zemer app's Latest Releases shelf (`https://flipphoneguy.duckdns.org/?page=zemer_releases`: a personal server of the Zemer team's, **not** `search.zemer.io`; rebuilt hourly, the last 14 days, newest first, an ETag, a release is a single when its `trackCount` is 1; `docs/youtube-music.md`). `createNewReleases` keeps the releases in the catalog's `zemer_releases` table and holds each to Zemer's artist list (listed, no women, nothing blocked, by the artist's channel id) when it is stored and again whenever it is listed, announced or alerted, so the owner's rule about the list holds here too. No release is stored as a song: its line is `single:<album id>` (opened through Zemer's album page, which sends the one song) or `album:<id>`, so everything after the 👍 is the code that menus already use, whitelist verdicts and the send-time gate included. `catalogBrowse(…, releases)` merges them with music-table.com's posts in `new` (newest first; a song or album both have is listed once, as Zemer's, by `releaseKey` in `src/ranking.ts`), and `new` reads the feed again first when it is over 15 minutes old, waiting at most 4 s for it (`Browse.refreshNew`). `LibraryJobs.syncReleases` reads it every 30 minutes; `buildDigest` takes them as `options.releases` (a music-table.com post for a song Zemer has is left out and counts as announced) and `alertFollowed` matches followed artists by name in either alphabet (`toAlert`). It is optional: a feed that fails is logged once, told (`onReleases`, a mailed problem) only after 12 hours, and music-table.com carries on alone. `ZEMER_RELEASES=off` turns it off. Covers are taken only from Google's picture hosts, and a row with a title over 200 characters is dropped, since the feed is not ours.
- **`src/sources/relevance.ts`**: what fits a request (`fitsAll`, `namesSong`, `rankSongs`), music-table.com's spelling fixes, and `soundsLike`, which reads a Latin-letter word against a Hebrew/Yiddish one ("vnusni" = "ונתנו"), because most of Zemer's titles are in Hebrew letters and requests are typed in Latin ones.
- **`src/sources/music-table.ts`** (+ `relevance.ts`, `titles.ts`): implements `TrackSource`. Site songs are stored as `…/post/<slug>#<n>` links, never download URLs, because the site's links expire; `resolvingAudio` fetches a fresh one at send time.
- **`src/sources/youtube-music.ts`**: where Zemer's songs' audio comes from, ported from Zemer (`ZemerTeam/zemer-app`): `search` as WEB_REMIX with the songs filter (only the fallback now), `player` as the VISIONOS client (ready-to-use links, no cipher or PoToken) for an AAC stream. Songs are stored as `https://music.youtube.com/watch?v=<id>`; `resolvingYouTubeAudio` wraps `resolvingAudio` the same way. The media server 403s without the client's User-Agent and a `Range` header, so downloads go through `YouTubeMusic.download`, not the plain `fetchAudio`. YouTube's player turns the cloud host away ("confirm you're not a bot"), so there every song comes through the Cloudflare Worker instead (`YouTubeMusicOptions.relay`, from `youTubeRelayFromEnv` in `src/cloud/youtube-relay.ts`, `YOUTUBE_RELAY=r2`): search and album pages are still asked directly, and the whitelist checks stay on the host. Zemer's other stream paths are not ported (`docs/youtube-music.md`). **Every Zemer and YouTube Music result goes through Zemer's artist whitelist (`src/sources/zemer-whitelist.ts`, the saved copy of what `content.zemer.io` used to serve) with female singers excluded, even though Zemer's server already filters, and a stored song is checked against the current list again when it is sent (`youTubeGate`, wrapped round `checkAudio` in every entry point). The owner requires both; `createZemerFinder` and `createYouTubeMusicSource` take the whitelist as a required argument so a new entry point can't skip it. Keep that if you touch these.** Since early November 2026 `content.zemer.io` (like `search.zemer.io`) answers only Zemer's signed app, and nothing here imitates it or reads Zemer's database behind it (the owner asked for an alternative, not a workaround; on 2026-11-08 they said to get around it or delete it, and it was deleted: **the bot no longer asks `content.zemer.io` at all**, `zemerWhitelistFromEnv` returns an `offline` list unless `ZEMER_CONTENT_URL` is set, so there is no request, no refusal and no mailed problem; no signing was built, so do not propose it): the saved copy is the list, frozen (`ZemerWhitelist.frozen`, always true offline; with the URL set, a 401/403 freezes it and it is asked again only every 3 hours), an artist that Zemer's public releases feed shows but the copy lacks *waits* (`consider`, `pending`; hidden until the owner 👍s it or texts `allow <name>`, because the feed doesn't say who is a woman), and `block <name>` hides anyone; these decisions live apart from Zemer's list (state `zemer.whitelist.owner`), a block always wins and an allow never lifts Zemer's female flag. The owner is told once about waiting artists (`src/waiting-notice.ts`); the chat commands are in `bot.ts` (`ArtistList`). `docs/youtube-music.md` has the details. `src/sources/songs.ts` puts the sources together for every entry point (`songSources`): the Zemer `finder` (asked first, and taken only when something has every word of the request, `fitsAll`), its `albums` opener, and music-table.com as `source` (catalog, then site), used when the finder has nothing or fails; `SONG_SOURCES=music-table,youtube-music` sets `musicTableFirst`.
- **`src/admin/`**: the owner's management console, served at `/admin/` by the cloud host's web door behind a sign-in (`docs/admin.md`). `console.ts` is the router (`AdminConsole`, the shared `adminConsole`) and the views; the door (`src/cloud/web.ts`, `CloudDeps.admin`) exists before the bot is loaded, so `cloud-main.ts` gives the console the host's part (`provide`: catalog, `/status`'s report, OneDrive, and `ConnectDeps` for the Connect tab: linking Google Messages through `Pairing`, finding and choosing the chat, OneDrive's sign-in, a test alert) and `host.ts` the bot's (whitelist, YouTube Music, releases, `library.jobs`, follows) once they exist; until then bot-only routes answer 503. **Sign-in** (`sign-in.ts`, `account.ts`; `CloudDeps.signIn` in `web.ts`, wired in `cloud-main.ts`): a real page at `/login`, the owner's own user name and password kept in the catalog state `admin.account` as a salted scrypt hash (set on the console's Account page, checked against the current password or `ADMIN_TOKEN`), sessions in state `admin.sessions` as SHA-256 of a random cookie token, each tied to the `ADMIN_TOKEN` it was opened under (`sessionBinding`: rotating the token signs every browser out) (14 days, 10 at most, `HttpOnly; SameSite=Lax`, `Secure` when `X-Forwarded-Proto` is https), eight wrong guesses a minute for the whole host. `ADMIN_TOKEN` stays the recovery and machine credential: any user name with it signs in on the page, and it works as a Bearer (or Basic) header for the Worker's `/status` check and `cloud:check`; the account's password signs in on the page only (a slow hash is not checked per request). The older POST routes in `web.ts` refuse a cookie-authenticated request that is not same-site (`isSameSite`). A browser asking for a page unsigned is redirected to `/login`; anything else gets 401 with no Basic prompt. Without `signIn` the door keeps its old Basic-password behaviour (the tests of it). Every change is a `POST` with JSON, `X-Admin-Console: 1`, a same-site `Origin`/`Sec-Fetch-Site` (the front door passes `X-Forwarded-Host`, replacing the visitor's), at most 64 KB and 60 a minute; the page is built with `textContent` only under a CSP with no inline script (a test greps for `innerHTML`). `settings.ts` lists every environment variable the code reads (a test greps `src/` and `deploy/cloud/` so a new one must be added) and the six **live** settings (`DIGEST_TIME`, `QUIET_HOURS`, `SONG_GAP_SECONDS`, `ALBUM_DOWNLOADS`, `DOWNLOADS_AHEAD`, `ONEDRIVE_MAX_MB_PER_MONTH`): they are read through `Live<T>` getters (`src/live.ts`) by `LibraryJobs`, the runner, `SongArchive` and the waiting notice, and stored as overrides in catalog state `admin.settings` over the environment; secrets show only "set" and are never sent to the page. `actions.ts` is the one-at-a-time guard with cooldowns; manual jobs go through `LibraryJobs.exclusive` so they never overlap the minute round. `audit.ts` keeps the console's changes (state `admin.audit`, 200 entries) and `log-ring.ts` the last 500 log lines in memory, masked (`tapConsole` taps `console.*`, installed first by `admin/capture.ts`). The artist rules it edits are in `ZemerWhitelist`: allowing needs `noWomenConfirmed: true`, a block wins, an allow never lifts Zemer's female flag, and a **per-song** layer (`allowSong`/`unblockSong`: an allowed song is still held to the artists credited on it now and when it was allowed, Zemer's blocked songs stay blocked until that very song is unblocked) is applied in `verdict` and so at send time through `youTubeGate`. It writes the catalog only when the owner changes something (Litestream), and has no way to edit Render.
- **People (the console's People tab, or `PEOPLE`; `src/people.ts`, `src/delivery-gate.ts`, `src/host.ts`, `src/cloud/seats.ts`, `src/cloud/people-list.ts`)**: built and deployed 2026-11-08; **the first person was added from the console and linked 2026-11-09 and works end to end** (the bridge accepts a second Matrix user at `user` level, a second Google login connects beside the owner's, the SIM number matched so their chat was found by itself, their search menu and a song reached Google with `at Google` about 9 s, and the host restart on Add was seen to come back). Still unwatched (`docs/cloud.md`, "Other people"): a second login's idle outbound traffic over a quiet night against Render's 5 GB, and Google's patience with two pairings from one datacenter address over days. Lessons from the first person: a new person's Connect window made several chats with the bridge's bot and the bridge answered commands in none of the ones it used (fixed: one chat, `!gm` prefix); Synapse's login allowance (fixed: `rc_login`); and the pasted request must be copied in a fresh private window signed in to ONLY their Google account, or the bridge links whichever account the window holds first (yours). One Matrix account, token, room, `Runner` and `Bot` per person inside the one bot process; the shared parts (catalog, Zemer's list, the song sources, library jobs, OneDrive, the console) are built once. **Invariant: with `PEOPLE` unset or empty and nothing saved in the bucket the owner's behaviour is exactly the old one**: same state keys, same table contents and column defaults, same wording, same start-up order; a new `Catalog` parameter for the person is a trailing optional `chat = ''`, so existing callers and tests compile unchanged. Model: `Person {id, owner, chat}`; `OWNER` is id `owner`, catalog chat `''`, the legacy unsuffixed keys; `parsePeople`/`peopleFromEnv` leave a bad name out and log it (never fatal; not `me`, `owner` or `gmessages*`, 2 to 16 lower-case letters or digits); `scoped(base, person)` is `base` for the owner and `base:<id>` for others; `tagLine` puts `[id]` in their log and timeline lines. **Adding and removing from the console (no Render variable)**: the owner types a name on the People tab; the names live in one small object in the R2 bucket, `config/people.json` (`PEOPLE_OBJECT`, `src/cloud/people-list.ts`: `readSavedPeople`, `mergePeople`, `PeopleList`), and `boot()` reads it once at the very start (`BootDeps.savedPeople`, built in `deploy/cloud/entrypoint.ts` from the bucket client; concurrent with the lease wait, tried twice, **never fatal**: absent says nothing, unreadable or damaged is one log line and the names in `PEOPLE` are used alone) and merges it with `PEOPLE` (the variable's names first, each once, at most `MAX_PEOPLE` = 10 in all; every stored name goes through `parsePeople` one at a time and again after the merge, because the bridge config is YAML and the account is made by a command line). The bot is told which names came from Render in `PEOPLE_IN_RENDER` (set by the host, a hand-set value is replaced) so the tab shows those as `set in Render` with no Remove button; its `PEOPLE` stays the merged list. A change takes effect only at a start (the bridge reads its permissions then, `register_new_matrix_user` needs `SECRET_KEY`, which only the host holds), so the console restarts the whole host: `PeopleDesk` (`src/cloud/people-desk.ts`) behind `POST /admin/api/people/add|remove|restart` (JSON, console header, same site, 60 a minute, audited by name only; remove and restart need `confirm: true` in the body; restart is refused unless the saved list differs from who is running, and while one is pending), `hostRestarter` (`src/cloud/host-restart.ts`) answers the page first and 3 s later sends `SIGUSR2` to the host process named by `HOST_PID` (set by the host for its children; never `process.ppid`), and `deploy/cloud/entrypoint.ts` stops everything as on SIGTERM and exits with code 1 so the container ends and Render starts it again (a clean exit is not known to be restarted; `onLost` uses 1 the same way); every start restores the databases from R2, which is why an in-process re-boot was rejected (the disk is not wiped, so a deploy that took the lease in the gap would have the stale databases written over its backup). The page keeps its `restarting…` state until `bootId` (the bot's start time, from `GET /admin/api/people` under `manage`) changes. Removing only changes the list: the person's data and bridge login stay, so the page tells the owner to unlink them on their Connect page first. With no bucket the Add route answers 409 saying so, and `PEOPLE` works as it did. **Per-person state**: `views.chat`, `plays.chat`, `follows` keyed `(chat, artist_id)` (rebuilt once, in one `BEGIN IMMEDIATE`, old rows become `''`), the `deliveries(chat, kind, key, at)` table for the daily message's and the alerts' marks (the owner's marks are also written to the old `announced_at`/`alerted_at` columns, for a rollback), and scoped state keys: `chat.view`, `chat.choices`, `chat.resume`, `hello.sent`, `digest.last_date|last_sent_at|retry_after|since`, `matrix.token|room|phone`, `bridge.seen`, `onboarding.linked|proved`, `usage.<month>.<id>.sent_bytes` plus the index `usage.<month>.people`; `message_links` `text:` keys carry the chat (`linksIn(catalog, chat)`). Shared: tracks, artists, site posts, release rows, the Zemer list. **The delivery gate** (`createDeliveryGate`, one per host): one file at a time host-wide (a song with the downloads it starts ahead, an album's round of songs coming to disk, a zip upload), round-robin between chats and FIFO within one, because the container holds one download (a 27 MB song is about +113 MB of 512; the 2026-10-18 kill); the song gap, cards, text answers and announcements are outside it, so a text is answered at once and an announcement never waits for it while holding `current`; `first: true` keeps a song's downloads and its upload together; `Runner.stop({abandon: true})` drops what has not started so a restart answers it. **Jobs**: `LibraryJobs.addRecipient(person, {announce, digestOffsetMinutes})` (a person added later is seeded with `digest.since:<id>` = now, so no surprise backlog); the daily message is at the host's time plus 5 minutes for each person, on the host's one clock and quiet hours; one recipient's failure is logged and never stops the others (the owner's is rethrown after the others' turns). **Owner-only**, and the places to check when adding a path: the bot gets `artistList` (allow, block, pending) and `assistant` only in `addChat` for the owner, so those words fall through to help for anyone else (and the send-time refusal for a blocked artist is reworded for a bot without `artistList`); the waiting-artist notice, the add-ons, OneDrive (a non-owner's `Library.forPerson(person).fetchAudio` never calls `archive.offer`), the console, `/status`, the Connect tab, the six live settings. **Zemer's rules apply to everybody**: every bot is built from the same `sources` and `checkAudio` objects, so the female-singer exclusion, the owner's allow/block, the per-song layer and the send-time gate hold for every person's results and sends (songs that come only from music-table.com are not held to Zemer's list, for anyone, as before). **Traffic**: each person's client counts its uploads (`sentCounter`), `PERSON_MAX_MB_PER_MONTH` (default 1000, `unlimited`) is a soft cap for non-owners (`monthlyAllowance`, `RunnerOptions.allowance`: an answer with audio is replaced by one marked text; searching still works), and the 4,000 MB alert sums everybody plus OneDrive copies. **Health, pairing, accounts**: see the `src/health.ts` and cloud-host bullets; boot makes each person's Matrix account (`register_new_matrix_user --no-admin`, password `derive(SECRET_KEY, 'user-<id>')`, handed to the bot as `PEOPLE_PASSWORDS`, `id:password` pairs, secret) and a `user` line in the bridge's permissions beside the owner's `admin`; a person's token never comes from `MATRIX_ACCESS_TOKEN`.
- **`src/health.ts`**: `Health` raises a problem report (mailed by the cloud host's Worker, a macOS notification on a Mac) because the chat can't report its own outage; `BridgeWatch` polls the bridge's login status and triggers `src/bridge-restart.ts` (the host's supervisor restarts the bridge on a signal; launchd on a Mac). Alert wording says "the host" and "restart the service in Render", never "this Mac". The bridge is one process for every person's login, so **only the owner's watch (`ownerBridge` in `src/host.ts`) restarts it**: a person's watch (`personBridge`, `BridgeWatch` with `person` and no `restart`, which it refuses to take) only reports, under `bridge:<id>`, `bridge-restart:<id>` and `rcs:<id>` in words that name them, asks the bridge with their own token, and says nothing until their login has been seen connected once (catalog state `bridge.seen:<id>`); `internet` stays one host-wide key.
- **`src/library/`** also owns file naming (`naming.ts`: `Artist/Album/01 Title.mp3`), tag writing (`id3.ts`, `mp4.ts`, hand-rolled, untouched audio; `mp4.ts` also rebuilds YouTube's fragmented M4A as an ordinary one), and every song sent goes through `taggedFetch` (`setup.ts`; an MP3 is tagged by `writeTagsToBlob`, which puts the new tag in front of the original audio as a slice of the same Blob, never reading or copying the audio, because a song costs the host several times its size otherwise; an M4A is rewritten as bytes), so the files on the phone carry their tags and cover: all the song's artists in the artist tag as `A; B` (`ARTIST_SEPARATOR`, so Musicolet can list it under each; the owner asked 2026-10-18), the folder's artist as album artist, and a Zemer song's album/number/year from the catalog's `album` column (filled from the album's page, `Finder.fillIn`). Also picture composition (`compose.ts` drives AppKit through `osascript`, so image features are macOS-only: on the Linux host a card falls back to the plain cover and the daily collage is skipped).
- **The cloud host** (`docs/cloud.md`): everything above can run in one Docker container on Render's free plan with a Cloudflare Worker beside it, so it doesn't depend on any home internet connection. `deploy/cloud/entrypoint.ts` (PID 1) calls `src/cloud/boot.ts`: take the lease (a file in the R2 bucket changed with conditional writes through `src/cloud/s3.ts`, `src/cloud/lease.ts`; at most one host at a time), restore the three SQLite databases from R2 with Litestream, write Synapse's and the bridge's settings (`src/cloud/provision.ts`; secrets derived from `SECRET_KEY`, so nothing is stored; the bridge's `matrix.message_status_events` is on, and `cloud-main.ts` sets `BRIDGE_STATUS_EVENTS=1` so the timelines wait for it), and keep the processes running (`src/cloud/supervise.ts`). `src/cloud-main.ts` is the bot's entry there: it opens the web door (`/healthz` and `/ping` open, `/status`, the console's Connect tab to link Google Messages and, if need be, choose the chat (the old `/pair` redirects there; its routes `/pair/send`, `/pair/log`, `/setup/rooms`, `/setup/room`, `/onedrive/*` remain for scripts), `/admin/import-catalog`), signs in, then imports `matrix-main.ts` (when `BOT_ENABLED` is on and it has a chat). With people in `PEOPLE` it instead builds the host (`startHost`) as soon as the owner is signed in, needing no room, and `src/cloud/seats.ts` (`Seats`, one `Seat` for each person, the owner first) adds each chat to it when that person's own room is joined: each seat has its own token (`ensureTokenPatiently` with the person's `MatrixAccount`, never the owner's `MATRIX_ACCESS_TOKEN`), `Pairing`, `RoomWatch` (Health key `room` for the owner, `room:<id>` and an alert naming the person for anyone else; state `matrix.room` / `matrix.phone` for the owner, `matrix.room:<id>` / `matrix.phone:<id>` for others; `MATRIX_ROOM_ID` is the owner's alone) and room search (`ownChatRooms` with that person's Matrix account, so one person's runner never binds to another's room), and a chat that goes away (room deleted on the phone) is taken off the host in-process (`removeChat`) while the seat waits for a new one, with nobody else affected; an account that can't be signed in is retried every minute (`SeatImpossible`: not at all). `/status` keeps the owner's fields and adds each person's entry to `people[]` (phase, `roomMissing`, bridge login, `simNumber`, `onboarding`, problems, what they were sent); the Connect routes and the older `/pair/*` / `/setup/*` routes take an optional `person` (`/pair?person=alice` leads to `#connect:alice`), and the console's People tab (`GET /admin/api/people`, read only, field by field from `/status`'s report) lists them. A person is **onboarded** only when `src/cloud/onboarding.ts` says so: their login is connected, their phone gave the bridge a SIM number (`Seat.hasSimNumber`: the self-chat patch fails open for a login with none and would copy all their chats, the 2026-10-29 suspension) and `ownChatRooms` found their own chat within 10 minutes of linking (a number that exists but does not match the chat never gets there); otherwise the page, `/status` and `cloud:check` (informational lines, `warn`, never a failure) say to unlink them. The Go patch is not changed. A pasted Google request is deleted from the person's chat by `Pairing` after a minute, and the pending deletion is kept in catalog state `pair.redactions` so the next start does it if the host restarted first. A person's `Pairing` opens its one chat with the bridge's bot once (single-flight: the Connect page asks from several requests at once the first time, and each used to make a chat of its own, so a new person ended with several and the bridge answered unprefixed commands in only one, 2026-11-08, "ari") and sends everything with the bridge's `!gm` prefix (`BRIDGE_COMMAND_PREFIX`), which any chat with the bot answers; the owner's window, whose chat has always been the one the bridge keeps for commands, sends none. It logs that it sent something (the size of a long message, never its text) and that the bot answered (never what it said). Removing a person: `logout <id>` from their own window (Connect tab) BEFORE they leave `PEOPLE`. With nobody in `PEOPLE` none of this runs and the start is the one described above. The host's own process (`deploy/cloud/entrypoint.ts`) holds the web port from its first moment to its last (`src/cloud/front-door.ts`): Render stops the old instance of a deploy only once the new one's port accepts a connection, and the old instance's stopping is what releases the lease, so a port that is closed at any point in a start gives visitors "Bad Gateway" and makes Render restart the instance (seen 2026-10-18). `/healthz` is answered there; everything else is passed to the bot's own door on `BOT_WEB_PORT` (8081, 127.0.0.1) or answered 503 with a self-reloading page that names the start's phase (`BootDeps.onPhase`). `boot.ts` makes the settings while it waits for the lease, restores the three databases at once, and the lease is polled every 1–2 s. Synapse's signing key is kept in the bucket (`keys/synapse-signing.key`, `BootDeps.signingKey`): Python makes it only on a start that finds none, since that is 15–20 s on this CPU. `/ping` answers 500 on purpose, for an uptime monitor that expects 500 (Render's loading page and gateway errors never say it). A chat deleted on the phone takes its room with it (the bridge deletes the room, and makes a new one under another id when the owner texts themself again; 2026-10-19, after which the bot answered nothing, then crashed and failed every start): `src/cloud/room.ts` (`RoomWatch`, used by `cloud-main.ts` before it imports `matrix-main.ts`) treats a 404/403 on joining the chosen room as "gone", not as a crash, so the start waits with the web door up, `/status` says `room-missing`/`roomGone`, `/pair` says so, and one alert is mailed through `Health`. It also finds the chat by itself (2026-10-25, after it was deleted again on 2026-10-22 and nobody chose it): `ownChatRooms` (`src/cloud/pairing.ts`) reads the bridge's database read-only for the one-to-one chat whose number is one of the phone's own (each SIM's `formattedPhoneNumber` in the login's metadata, or the number of the chat used before, catalog state `matrix.phone`), and the watch takes it once the given rooms can't be joined, so texting yourself again is all it takes; choosing on `/pair` still works. A 429 on a join is waited out (Synapse counts a join to a room it no longer has as a federated join, which its defaults allow once per 100 s; `rc_joins` is raised in `provision.ts`); `watchJoinedRoom` makes the running bot check its room every five minutes and stop when it is gone, so the next start lands in that waiting state. An announcement the chat refuses is the announcer's to handle (`exclusive` in `runner.ts` keeps the failure out of `current`): it used to reach the poll loop and crash the bot. On its first start the bot says hello in the chat once (`src/startup-message.ts`, `STARTUP_MESSAGE`). The runner saves how far it got (`ResumeStore`, catalog state `chat.resume`) so a restart answers texts sent while it was down. Problems are left as files in the bucket's `alerts/` folder (`src/alert.ts`) and mailed by the Cloudflare Worker's five-minute job (`cloudflare/`); the host never calls the Worker, because Cloudflare challenges every automated client on workers.dev. With `ONEDRIVE_CLIENT_ID` set, every song the library fetches to send is also offered to `SongArchive` (`src/archive/archiver.ts`), which uploads it, exactly as it was sent (it is already tagged by `taggedFetch`, so it is not tagged or copied again: it goes up from its Blob a 10 MiB piece at a time), to the owner's OneDrive app folder in the background through `src/archive/onedrive.ts` (device-code sign-in done from the `/pair` page, refresh token in catalog state `onedrive.refresh`, a monthly upload allowance because Render's free plan caps outbound traffic). Live since 2026-10-16; `docs/cloud.md` lists what was proven and what is still open (OneDrive has been saving songs since 2026-10-18; an album delivered as one zip through the patched bridge had not gone out live yet as of 2026-10-20). `src/cloud/memory.ts` (`MemoryWatch`, started by `cloud-main.ts`) logs which process holds the container's memory (`memory:` lines past 85% of the limit, a routine line after each start and every six hours) and puts the breakdown and the highest reading in `/status` under `memory`; the host's first out-of-memory kill (2026-10-18) took a 27 MB MP3 on top of 334 MB already in use. The bridge is built from upstream `186284e` with every patch in `deploy/cloud/patches/` (their Go tests run in the Dockerfile): the streaming one (which also logs `media to Google: … MB, homeserver …s, encrypt+upload …s`), `gmessages-only-self-chat.patch` (below), and `gmessages-dedup-dm-txn.patch`, upstream's `dbbd04de`: `deduplicateDM` deleted on the outer context inside its own `_txlock=immediate` transaction, waited 5 s for its own lock and failed on every self-chat event, holding every other bridge write (a 10-line reply reached Google over 47.5 s; found 2026-10-20). A cherry-pick, not a newer pin (newer `main` bumps mautrix-go, which can carry a migration that blocks a rollback). `/status` also has `timings` (the last 20 timeline lines). Past 4,000 MB of songs sent plus OneDrive copies in a month the bot raises a mailed problem (`trafficProblem`, `src/usage.ts`). The relay's request is named `<video id>-<random>-<most bytes>` so the Worker answers it without reading it, the Worker keeps a YouTube session 30 minutes and reports its timings in its answer, and the host polls every 400 ms and cleans up in the background. OneDrive copies wait while the runner is `busy()`. Gotchas learned on real R2: conditional writes need strong ETags (`accept-encoding: identity`), and the free plan's tenth of a CPU makes the bridge slow to make rooms after pairing. The bridge keeps to the self-chat (`gmessages-only-self-chat.patch`, 2026-10-30: a conversation that isn't one-to-one with one of the phone's own SIM numbers is dropped as it arrives; `GMESSAGES_ALL_CHATS=1` undoes it): copying every chat into Synapse made Litestream's uploads most of the host's traffic, and the service went over Render's 5 GB a month on 2026-10-29 and was suspended to the month's end. Litestream captures changes every 5 minutes with one hourly merge for the same reason (`deploy/cloud/litestream.yml`); keep both in mind before adding anything that writes to a database often (`docs/privacy-and-security.md`, `docs/cloud.md`).
- **`extensions/`** is gitignored (each add-on can be its own repo) but is still typechecked and tested. An add-on's `index.ts` default-exports an `ExtensionSetup` (`src/extensions.ts`); only the bridge route loads them (the cloud image does not include `extensions/`, so an add-on does not run there), and a failing one is reported and skipped rather than stopping the bot.

## Conventions and constraints

- `tsconfig` uses `erasableSyntaxOnly`, `verbatimModuleSyntax`, `noUncheckedIndexedAccess` and `allowImportingTsExtensions`: no enums, namespaces or parameter properties; use `import type`; import local files with their `.ts` extension.
- Entry points `import './load-env.ts'` first (loads `.env`; real environment variables win).
- Every message the bot sends starts with `BOT_MARK` (🎵) or one of `KIND_MARKS` (💿 an album line, 🎤 an artist, 📦 an album's zip), except a menu's closing line where a 👍 picks ('Text "songs more" for 8 more songs…'), which starts with `HINT_MARK`, an invisible left-to-right mark (`markHint`): it isn't a song, and the owner asked for no 🎵 on it (2026-10-18). Add-on relays start with `RELAY_MARK` (🤖); the runner never answers a message starting with any of them. `markBotText` also puts invisible left-to-right marks after the mark and after each stretch of Hebrew followed by something else, or the phone shows a Hebrew title's line turned round. The self-chat is shared by the bot and the user, so this is the loop guard; keep it when adding message types. The runner also treats a word-for-word repeat within 20 seconds as an echo of the first (a phone can show one text twice) and caps answers per minute (`maxAnswersPerMinute`, 30; not messages, because a long list such as an album's 50 songs is one answer and must arrive whole; Synapse's own message limit is lifted in `provision.ts` for the same reason, 2026-10-19).
- Downloads must be audio, within `MAX_DOWNLOAD_MB`, and from a source's own HTTPS hosts (music-table.com's file hosts, YouTube's `googlevideo.com`); page links are rejected. music-table.com's source only ever uses the files its posts offer: the YouTube embeds in those posts are ignored. YouTube Music is a separate, deliberate source (added 2026-10-11 at the owner's request, overriding the earlier rule against it).
- The simulator binds 127.0.0.1 only. The cloud host's web door (`src/cloud/web.ts`) binds 0.0.0.0 because Render needs a public port: only `/healthz` and `/ping` are open, everything else needs `ADMIN_TOKEN`, and the homeserver and bridge stay on 127.0.0.1. (The RBM webhook, `src/server.ts`, also binds all interfaces.)
- Tests are `node:test` with mock servers for Matrix, music-table.com, Beeper, Google's RBM API and an audio host (`test/helpers/`); new behavior against those services should extend the mocks, not hit the network.
- `.env`, `data/`, `*.db`, `keys/`, `extensions/` and `.claude/` are gitignored. `deploy/dell/` is an abandoned Windows/WSL setup (also ignored); don't revive it.
