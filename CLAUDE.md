# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal bot: you text `search <words>` in your own Google Messages "message yourself" chat, get a menu of artists, albums and songs like a streaming app's, and a 👍 on a song sends back the audio file with album art (on an album, its songs and a zip of them). It reaches the phone through a self-hosted mautrix-gmessages bridge and a Matrix (Synapse) homeserver, which run with the bot in one Docker container on Render's free plan (a Cloudflare Worker and an R2 bucket beside it); since 2026-10-16 that is the only place it runs, and the Mac install was removed. Songs come first from Zemer's catalog (`search.zemer.io`, the service the Zemer app searches with: albums and singles of the artists on Zemer's list, audio from YouTube Music through the same InnerTube API the app uses), and, for what Zemer doesn't have, from a local SQLite catalog fed by music-table.com (direct MP3 downloads of mostly new singles on its release posts). New music (the `new` list, the daily message and the alerts for artists you follow) is Zemer's own Latest Releases feed and music-table.com's posts together (the owner's request, 2026-10-28: "Make zemer also the source for new releases"). `README.md` covers the user-facing behavior; `docs/architecture.md` is the fuller code tour.

## Commands

TypeScript runs directly on Node ≥ 22.18 (no build step), and there are **no runtime dependencies** (`node:sqlite`, `node:http`, built-in `fetch`). `npm install` only brings in `typescript` and `@types/node`.

```bash
npm test                          # whole suite, no network (mock servers in test/helpers/)
npm run typecheck                 # tsc, noEmit; covers src, scripts, test and extensions
npm run simulate:web -- --open    # real bot + real site in a browser chat; needs no accounts
npm run matrix                    # run the bridge-route bot in the foreground (needs .env)
npm run library -- <cmd>          # status | sync | scan | prefetch | digest [--days N] [--send]
ADMIN_TOKEN=… npm run cloud:check -- --render https://music-over-rcs.onrender.com   # is the live host, bridge, bot and Worker healthy
```

Run one test file, or one test by name (invoke `node` directly; `npm test` takes a fixed glob):

```bash
node --disable-warning=ExperimentalWarning --test test/naming.test.ts
node --disable-warning=ExperimentalWarning --test --test-name-pattern="restart" test/bridge-restart.test.ts
```

There is no linter or formatter configured.

## The running bot is on Render, not this folder

The live bot runs from the Docker image Render builds from the `main` branch (service `music-over-rcs`, id `srv-db8nrt6i0phs738cf5lg`, Ohio, free plan; `docs/cloud.md` is the runbook). **Nothing here reaches it until you push and deploy**: push to `main`, then deploy by hand (Render dashboard → *Manual Deploy*, or the Render MCP's `trigger_deploy`); `autoDeploy` is off on purpose. A deploy restarts the bot (about a minute down; texts sent meanwhile are answered afterwards), and deploys queue behind each other, so do not stack them. Changing an environment variable in Render restarts it too, and `.env` here is only for local runs. The live catalog is in the container, backed up to R2; `data/catalog.db` is only what a local `npm run …` uses. The Mac install (`deploy/mac`, launchd) is gone; do not bring it back next to the cloud host, because two bots in one chat both answer. **No more money** (the owner, 2026-10-20): everything stays on Render's free plan and the Cloudflare Workers plan already paid for; recommend only $0 changes (`docs/cloud.md`, "What it costs").

## Architecture

Three layers, in the order a message travels:

1. **Transport** (`ChatClient`: `listMessages`, `sendText`, `sendAudio`, optional `sendImage`, `sendFile` (the album zip), `setTyping`). Implementations: `src/matrix/` (the main route), `src/beeper/`, and the simulator's `SimulatedChat`. The RCS for Business route (`src/rbm/`, `src/handler.ts`, `src/server.ts`, entry `npm start`) is a separate webhook server that calls the bot directly and doesn't get the library features.
2. **`src/runner.ts`** binds the bot to one chat: reads it (a long poll where the chat can, `waitMs`/`MATRIX_SYNC_WAIT_MS`, 25 s; an announcement or stop aborts the wait), ignores its own messages, handles 👍 reactions, numbers, `all`, typing indicators, downloading ahead (an album's songs three at a time, `albumDownloads`/`ALBUM_DOWNLOADS`, each to disk as it arrives, held back by `memoryRoom` and a 40 MB in-flight budget, one at a time after YouTube turned the relay away), spacing audio files by `SONG_GAP_SECONDS`, and sends bot-initiated messages through `announce` (never in the middle of answering a request). Reading the chat never waits for a song on its way (owner's report 2026-10-18): a poll looks each request up and sends a text answer at once, while an answer with a song, picture or album joins a delivery queue (`send`) that runs one at a time in the order asked, because songs must arrive in that order and the host can't hold two downloads. An answer's options (its chips and numbers) apply when it is decided, not when it has been sent, and only an answer with options of its own replaces them (an unrelated text leaves a menu pickable; a pick refreshes its two hours). "typing…" stays up while any request is open, and the resume point is saved only when nothing is queued. Each request leaves a `timeline:` line (`src/timeline.ts`: phone→seen, the bot's traced steps, each send, and with `sendStatus` the bridge's word that Google had the messages), each song a `song:` line, each album an `album:` line; `onTimeline` hands them to `/status`. `Runner.tick()` still returns when everything it started has been sent (the tests rely on it); the poll loop uses `poll()`.
3. **`src/bot.ts`** decides what to answer and knows nothing about platforms. It takes text or a postback and returns `Reply[]` (`text`, `image`, `collage`, `audio`, `album`; see `src/types.ts`). **A search is a menu, never a pick** (the owner's design, 2026-10-20; `Fixing PLan.md`): up to 5 artists (🎤), 5 albums (💿, numbered) and 5 songs, one message per line, ranked by `src/ranking.ts` (artists exact > started > a typo away; songs named > every word in the title > only with the artist, most played first; albums named > newest; editions folded), written by `src/menu.ts`, ending with a hint line (`HINT_MARK`) whose postback is `view:<id>`. Nothing is sent or opened on its own, not one exactly named song, not an artist's full name. Every menu, artist page (`artist:<id>`), album (`album:`/`tracks:<id>`: its songs numbered as on the album and a `📦` line, `zip:<id>`) and music-table list is a **view** (`src/views.ts`, catalog table `views`, ids never reused, current one in state `chat.view`): what it is of, and every line it has shown. `songs more`/`albums more`/`artists more` re-ask the source (Zemer's answers are kept 10 minutes), skip what was shown and show the next 8, walking up to the parent view when the current one lacks that kind; bare `more` repeats the last. Every line's postback carries its view (`play:42@41`, `splitPostback`), so a 👍 on a line of an older menu makes it current again; an answer that changes the current view without a list of its own carries that view's options (an empty-text chips reply). Commands: `search`, `artist`/`album`/`song` (one-kind menus; `albums more` is paging, `albums <name>` a search), `zemer` (`youtube`/`yt`), `zip`, `all`, `help` (one message, `helpText`), the music-table lists (`new` also lists Zemer's new releases: `single:<id>` and `album:<id>` lines), follow. Old postbacks still work (`album:` without a view now opens the album). `play()` starts the album lookup (`Finder.fillIn`) alongside the download: the card's `better` cover and the audio's `after` hand-off, which `taggedFetch` waits for before tagging. Slow steps are traced (`handle(msg, trace)`, through an `AsyncLocalStorage`). An `album` reply is a list of song addresses; the runner downloads them to a temporary folder and sends one zip made of the files on disk (`src/library/zip.ts`), split only past `MAX_ZIP_MB` (100: the bridge's and the homeserver's limit), or the songs one by one on a chat with no `sendFile`. The owner wants an album as one zip, not parts (2026-10-18); that is why nothing on the way holds it in memory: the disk folder, the Matrix client's streamed `node:http` upload (Node's `fetch` buffers a whole body), and the bridge patch `deploy/cloud/patches/gmessages-stream-media.patch` (`docs/cloud.md`). The golden menus are tested against what Zemer really answered (`test/fixtures/zemer`, `test/menu.test.ts`).

Entry points wire these together: `src/matrix-main.ts` is the best single file to read for how everything is assembled (catalog, music-table source, library jobs, health, bridge watch, extensions, runner).

Behind the bot:

- **`src/catalog.ts`**: one SQLite file (WAL, shared with the CLI tools): tracks + FTS, artists, site posts, plays, follows, audio cache, `message_links`, and a `state` key/value table. The background jobs persist their progress there, so restarts resume.
- **`src/library/jobs.ts`** (`LibraryJobs`): ticks once a minute, doing one thing at a time (site sync every 3 h, Zemer's new-releases feed every 30 min, prefetch, RSS check every 15 min while following anyone, daily message, follow alerts outside quiet hours, one-time full-site scan). The daily message and the alerts carry Zemer's releases beside the site's. The library tests drive it on a fake clock.
- **`src/sources/zemer.ts`**: Zemer's catalog. `ZemerSearch` is the client for `search.zemer.io` (`/search` sorted into artists, songs, videos, albums, singles, `k=50` because Zemer's order isn't by plays; `/artist`; `/album`; always `allowFemale=0&blockVideos=0&kidZone=0`, since the server leaves in whatever isn't said; searches, artist and album pages kept 10 minutes). `find` returns each song's `id` (video id), `plays` and `video`, folds duplicates keeping the most played copy, lists a video only when no song has it, and returns singles apart from albums (`Findings.singles`; the menu lists a single as a song). `createZemerFinder` makes it the bot's `Finder` (and its `albums` opener): it re-checks every result against the local whitelist by channel id, stores only the songs it shows (`FoundSong.keep`), and falls back to YouTube Music's own InnerTube search when Zemer can't be reached or `ZEMER_SEARCH=off`. A song with no cover gets its album's at send time (`Finder.cover`). The owner wants Zemer first and music-table.com only as the fallback (2026-10-17): "If both have it, rather use Zemer."
- **`src/sources/zemer-releases.ts`**: Zemer as a source of new releases. `ZemerReleases` reads the feed behind the Zemer app's Latest Releases shelf (`https://flipphoneguy.duckdns.org/?page=zemer_releases`: a personal server of the Zemer team's, **not** `search.zemer.io`; rebuilt hourly, the last 14 days, newest first, an ETag, a release is a single when its `trackCount` is 1; `docs/youtube-music.md`). `createNewReleases` keeps the releases in the catalog's `zemer_releases` table and holds each to Zemer's artist list (listed, no women, nothing blocked, by the artist's channel id) when it is stored and again whenever it is listed, announced or alerted, so the owner's rule about the list holds here too. No release is stored as a song: its line is `single:<album id>` (opened through Zemer's album page, which sends the one song) or `album:<id>`, so everything after the 👍 is the code that menus already use, whitelist verdicts and the send-time gate included. `catalogBrowse(…, releases)` merges them with music-table.com's posts in `new` (newest first; a song or album both have is listed once, as Zemer's, by `releaseKey` in `src/ranking.ts`), and `new` reads the feed again first when it is over 15 minutes old, waiting at most 4 s for it (`Browse.refreshNew`). `LibraryJobs.syncReleases` reads it every 30 minutes; `buildDigest` takes them as `options.releases` (a music-table.com post for a song Zemer has is left out and counts as announced) and `alertFollowed` matches followed artists by name in either alphabet (`toAlert`). It is optional: a feed that fails is logged once, told (`onReleases`, a mailed problem) only after 12 hours, and music-table.com carries on alone. `ZEMER_RELEASES=off` turns it off. Covers are taken only from Google's picture hosts, and a row with a title over 200 characters is dropped, since the feed is not ours.
- **`src/sources/relevance.ts`**: what fits a request (`fitsAll`, `namesSong`, `rankSongs`), music-table.com's spelling fixes, and `soundsLike`, which reads a Latin-letter word against a Hebrew/Yiddish one ("vnusni" = "ונתנו"), because most of Zemer's titles are in Hebrew letters and requests are typed in Latin ones.
- **`src/sources/music-table.ts`** (+ `relevance.ts`, `titles.ts`): implements `TrackSource`. Site songs are stored as `…/post/<slug>#<n>` links, never download URLs, because the site's links expire; `resolvingAudio` fetches a fresh one at send time.
- **`src/sources/youtube-music.ts`**: where Zemer's songs' audio comes from, ported from Zemer (`ZemerTeam/zemer-app`): `search` as WEB_REMIX with the songs filter (only the fallback now), `player` as the VISIONOS client (ready-to-use links, no cipher or PoToken) for an AAC stream. Songs are stored as `https://music.youtube.com/watch?v=<id>`; `resolvingYouTubeAudio` wraps `resolvingAudio` the same way. The media server 403s without the client's User-Agent and a `Range` header, so downloads go through `YouTubeMusic.download`, not the plain `fetchAudio`. YouTube's player turns the cloud host away ("confirm you're not a bot"), so there every song comes through the Cloudflare Worker instead (`YouTubeMusicOptions.relay`, from `youTubeRelayFromEnv` in `src/cloud/youtube-relay.ts`, `YOUTUBE_RELAY=r2`): search and album pages are still asked directly, and the whitelist checks stay on the host. Zemer's other stream paths are not ported (`docs/youtube-music.md`). **Every Zemer and YouTube Music result goes through Zemer's artist whitelist (`src/sources/zemer-whitelist.ts`, read from `content.zemer.io`) with female singers excluded, even though Zemer's server already filters, and a stored song is checked against the current list again when it is sent (`youTubeGate`, wrapped round `checkAudio` in every entry point). The owner requires both; `createZemerFinder` and `createYouTubeMusicSource` take the whitelist as a required argument so a new entry point can't skip it. Keep that if you touch these.** `src/sources/songs.ts` puts the sources together for every entry point (`songSources`): the Zemer `finder` (asked first, and taken only when something has every word of the request, `fitsAll`), its `albums` opener, and music-table.com as `source` (catalog, then site), used when the finder has nothing or fails; `SONG_SOURCES=music-table,youtube-music` sets `musicTableFirst`.
- **`src/health.ts`**: `Health` raises a problem report (mailed by the cloud host's Worker, a macOS notification on a Mac) because the chat can't report its own outage; `BridgeWatch` polls the bridge's login status and triggers `src/bridge-restart.ts` (the host's supervisor restarts the bridge on a signal; launchd on a Mac). Alert wording says "the host" and "restart the service in Render", never "this Mac".
- **`src/library/`** also owns file naming (`naming.ts`: `Artist/Album/01 Title.mp3`), tag writing (`id3.ts`, `mp4.ts`, hand-rolled, untouched audio; `mp4.ts` also rebuilds YouTube's fragmented M4A as an ordinary one), and every song sent goes through `taggedFetch` (`setup.ts`; an MP3 is tagged by `writeTagsToBlob`, which puts the new tag in front of the original audio as a slice of the same Blob, never reading or copying the audio, because a song costs the host several times its size otherwise; an M4A is rewritten as bytes), so the files on the phone carry their tags and cover: all the song's artists in the artist tag as `A; B` (`ARTIST_SEPARATOR`, so Musicolet can list it under each; the owner asked 2026-10-18), the folder's artist as album artist, and a Zemer song's album/number/year from the catalog's `album` column (filled from the album's page, `Finder.fillIn`). Also picture composition (`compose.ts` drives AppKit through `osascript`, so image features are macOS-only: on the Linux host a card falls back to the plain cover and the daily collage is skipped).
- **The cloud host** (`docs/cloud.md`): everything above can run in one Docker container on Render's free plan with a Cloudflare Worker beside it, so it doesn't depend on any home internet connection. `deploy/cloud/entrypoint.ts` (PID 1) calls `src/cloud/boot.ts`: take the lease (a file in the R2 bucket changed with conditional writes through `src/cloud/s3.ts`, `src/cloud/lease.ts`; at most one host at a time), restore the three SQLite databases from R2 with Litestream, write Synapse's and the bridge's settings (`src/cloud/provision.ts`; secrets derived from `SECRET_KEY`, so nothing is stored; the bridge's `matrix.message_status_events` is on, and `cloud-main.ts` sets `BRIDGE_STATUS_EVENTS=1` so the timelines wait for it), and keep the processes running (`src/cloud/supervise.ts`). `src/cloud-main.ts` is the bot's entry there: it opens the web door (`/healthz` and `/ping` open, `/status`, `/pair` to link Google Messages and, if need be, choose the chat, `/admin/import-catalog`), signs in, then imports `matrix-main.ts` (when `BOT_ENABLED` is on and it has a chat). The host's own process (`deploy/cloud/entrypoint.ts`) holds the web port from its first moment to its last (`src/cloud/front-door.ts`): Render stops the old instance of a deploy only once the new one's port accepts a connection, and the old instance's stopping is what releases the lease, so a port that is closed at any point in a start gives visitors "Bad Gateway" and makes Render restart the instance (seen 2026-10-18). `/healthz` is answered there; everything else is passed to the bot's own door on `BOT_WEB_PORT` (8081, 127.0.0.1) or answered 503 with a self-reloading page that names the start's phase (`BootDeps.onPhase`). `boot.ts` makes the settings while it waits for the lease, restores the three databases at once, and the lease is polled every 1–2 s. Synapse's signing key is kept in the bucket (`keys/synapse-signing.key`, `BootDeps.signingKey`): Python makes it only on a start that finds none, since that is 15–20 s on this CPU. `/ping` answers 500 on purpose, for an uptime monitor that expects 500 (Render's loading page and gateway errors never say it). A chat deleted on the phone takes its room with it (the bridge deletes the room, and makes a new one under another id when the owner texts themself again; 2026-10-19, after which the bot answered nothing, then crashed and failed every start): `src/cloud/room.ts` (`RoomWatch`, used by `cloud-main.ts` before it imports `matrix-main.ts`) treats a 404/403 on joining the chosen room as "gone", not as a crash, so the start waits with the web door up, `/status` says `room-missing`/`roomGone`, `/pair` says so, and one alert is mailed through `Health`. It also finds the chat by itself (2026-10-25, after it was deleted again on 2026-10-22 and nobody chose it): `ownChatRooms` (`src/cloud/pairing.ts`) reads the bridge's database read-only for the one-to-one chat whose number is one of the phone's own (each SIM's `formattedPhoneNumber` in the login's metadata, or the number of the chat used before, catalog state `matrix.phone`), and the watch takes it once the given rooms can't be joined, so texting yourself again is all it takes; choosing on `/pair` still works. A 429 on a join is waited out (Synapse counts a join to a room it no longer has as a federated join, which its defaults allow once per 100 s; `rc_joins` is raised in `provision.ts`); `watchJoinedRoom` makes the running bot check its room every five minutes and stop when it is gone, so the next start lands in that waiting state. An announcement the chat refuses is the announcer's to handle (`exclusive` in `runner.ts` keeps the failure out of `current`): it used to reach the poll loop and crash the bot. On its first start the bot says hello in the chat once (`src/startup-message.ts`, `STARTUP_MESSAGE`). The runner saves how far it got (`ResumeStore`, catalog state `chat.resume`) so a restart answers texts sent while it was down. Problems are left as files in the bucket's `alerts/` folder (`src/alert.ts`) and mailed by the Cloudflare Worker's five-minute job (`cloudflare/`); the host never calls the Worker, because Cloudflare challenges every automated client on workers.dev. With `ONEDRIVE_CLIENT_ID` set, every song the library fetches to send is also offered to `SongArchive` (`src/archive/archiver.ts`), which uploads it, exactly as it was sent (it is already tagged by `taggedFetch`, so it is not tagged or copied again: it goes up from its Blob a 10 MiB piece at a time), to the owner's OneDrive app folder in the background through `src/archive/onedrive.ts` (device-code sign-in done from the `/pair` page, refresh token in catalog state `onedrive.refresh`, a monthly upload allowance because Render's free plan caps outbound traffic). Live since 2026-10-16; `docs/cloud.md` lists what was proven and what is still open (OneDrive has been saving songs since 2026-10-18; an album delivered as one zip through the patched bridge had not gone out live yet as of 2026-10-20). `src/cloud/memory.ts` (`MemoryWatch`, started by `cloud-main.ts`) logs which process holds the container's memory (`memory:` lines past 85% of the limit, a routine line after each start and every six hours) and puts the breakdown and the highest reading in `/status` under `memory`; the host's first out-of-memory kill (2026-10-18) took a 27 MB MP3 on top of 334 MB already in use. The bridge is built from upstream `186284e` with every patch in `deploy/cloud/patches/` (their Go tests run in the Dockerfile): the streaming one (which also logs `media to Google: … MB, homeserver …s, encrypt+upload …s`), and `gmessages-dedup-dm-txn.patch`, upstream's `dbbd04de`: `deduplicateDM` deleted on the outer context inside its own `_txlock=immediate` transaction, waited 5 s for its own lock and failed on every self-chat event, holding every other bridge write (a 10-line reply reached Google over 47.5 s; found 2026-10-20). A cherry-pick, not a newer pin (newer `main` bumps mautrix-go, which can carry a migration that blocks a rollback). `/status` also has `timings` (the last 20 timeline lines). Past 4,000 MB of songs sent plus OneDrive copies in a month the bot raises a mailed problem (`trafficProblem`, `src/usage.ts`). The relay's request is named `<video id>-<random>-<most bytes>` so the Worker answers it without reading it, the Worker keeps a YouTube session 30 minutes and reports its timings in its answer, and the host polls every 400 ms and cleans up in the background. OneDrive copies wait while the runner is `busy()`. Gotchas learned on real R2: conditional writes need strong ETags (`accept-encoding: identity`), and the free plan's tenth of a CPU makes the bridge slow to make rooms after pairing. The bridge makes rooms for the 25 most recent chats on pairing and relays every chat's messages while it runs; Synapse keeps them (`docs/privacy-and-security.md`).
- **`extensions/`** is gitignored (each add-on can be its own repo) but is still typechecked and tested. An add-on's `index.ts` default-exports an `ExtensionSetup` (`src/extensions.ts`); only the bridge route loads them (the cloud image does not include `extensions/`, so an add-on does not run there), and a failing one is reported and skipped rather than stopping the bot.

## Conventions and constraints

- `tsconfig` uses `erasableSyntaxOnly`, `verbatimModuleSyntax`, `noUncheckedIndexedAccess` and `allowImportingTsExtensions`: no enums, namespaces or parameter properties; use `import type`; import local files with their `.ts` extension.
- Entry points `import './load-env.ts'` first (loads `.env`; real environment variables win).
- Every message the bot sends starts with `BOT_MARK` (🎵) or one of `KIND_MARKS` (💿 an album line, 🎤 an artist, 📦 an album's zip), except a menu's closing line where a 👍 picks ('Text "songs more" for 8 more songs…'), which starts with `HINT_MARK`, an invisible left-to-right mark (`markHint`): it isn't a song, and the owner asked for no 🎵 on it (2026-10-18). Add-on relays start with `RELAY_MARK` (🤖); the runner never answers a message starting with any of them. `markBotText` also puts invisible left-to-right marks after the mark and after each stretch of Hebrew followed by something else, or the phone shows a Hebrew title's line turned round. The self-chat is shared by the bot and the user, so this is the loop guard; keep it when adding message types. The runner also treats a word-for-word repeat within 20 seconds as an echo of the first (a phone can show one text twice) and caps answers per minute (`maxAnswersPerMinute`, 30; not messages, because a long list such as an album's 50 songs is one answer and must arrive whole; Synapse's own message limit is lifted in `provision.ts` for the same reason, 2026-10-19).
- Downloads must be audio, within `MAX_DOWNLOAD_MB`, and from a source's own HTTPS hosts (music-table.com's file hosts, YouTube's `googlevideo.com`); page links are rejected. music-table.com's source only ever uses the files its posts offer: the YouTube embeds in those posts are ignored. YouTube Music is a separate, deliberate source (added 2026-10-11 at the owner's request, overriding the earlier rule against it).
- The simulator binds 127.0.0.1 only. The cloud host's web door (`src/cloud/web.ts`) binds 0.0.0.0 because Render needs a public port: only `/healthz` and `/ping` are open, everything else needs `ADMIN_TOKEN`, and the homeserver and bridge stay on 127.0.0.1. (The RBM webhook, `src/server.ts`, also binds all interfaces.)
- Tests are `node:test` with mock servers for Matrix, music-table.com, Beeper, Google's RBM API and an audio host (`test/helpers/`); new behavior against those services should extend the mocks, not hit the network.
- `.env`, `data/`, `*.db`, `keys/`, `extensions/` and `.claude/` are gitignored. `deploy/dell/` is an abandoned Windows/WSL setup (also ignored); don't revive it.
